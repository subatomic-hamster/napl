# STS3215 servo-loop calibration and contact data (stage N6 research)

Accessed 2026-10-07 (every URL below was fetched on this date unless marked otherwise). Builds on `docs/research/so101.md` (servo datasheet table, DC-motor equivalent, MJCF gains); that material is not repeated here.
Sim law under test (`src/mujoco/devices/servo.cpp`, `docs/models.md`): `duty = (p*e + i*sum(e) + d*(e - e_prev)) / pid_scale`, e in encoder counts (4096/rev), clamp `max_torque/1000`. Static stiffness `K = (p/pid_scale) * tau_stall(V) * 4096/(2*pi)` N*m/rad.
Constants used in all arithmetic: 1 count = 2*pi/4096 = 1.53398e-3 rad = 0.087891 deg; 4096/(2*pi) = 651.899 counts/rad; tau_stall = 1.32 N*m (5 V, model), 1.912 N*m (7.4 V, datasheet), 2.94 N*m (12 V, 30 kg.cm * 9.8 / 100).
Local clones used for quotes (scratch, not committed): Rhoban/bam `e9a619d` (2026-09-13), ftservo/ftservo-bam `4f7c0b0` (2026-09-30), ftservo/ftservo-wiki `f1387d3` (2026-10-05), Gregory119/RBE501-RL-arm-project `58ae9dd` (2025-11-01), huggingface/lerobot `200ee53596d464bd28f6595cdb31be69a2b5e379` (2026-10-06), ftservo/FTServo_Python `cbcfa64` (2026-09-29), Adam-Software/Feetech-Servo-SDK `5d25bbe` (2022-11-08).

## 1. PID register scaling evidence

### 1.0 What the law must reproduce

Two things are separable: (a) duty per count per unit P (firmware, the thing `pid_scale` encodes) and (b) torque per unit duty (motor model, already validated to +/-10 % against the datasheet in `so101.md`). `pid_scale` should be fitted on (a) only. Evidence that mixes in a torque assumption is converted to `pid_scale` below with the torque assumption stated.

### 1.1 Gregory119 RBE501 README (source of MJCF kp = 998.22)

- URLs: https://github.com/Gregory119/RBE501-RL-arm-project/blob/main/gymnasium_env/README.md and `.../calc_actuator_model.py` (raw files read, commit `58ae9dd`).
- README quotes: "This script assumes that the servo proportional gain is set to a specific value (see script) - if this gain is changed then these model values need to be recalculated." and "It is assumed that the PID controller of the servo is set to only use a proportional gain term ($G_p$), and that the position error is in degrees instead of radians. This gives the voltage applied to the motor by the servo PID controller as: $$ V = G_p e = G_p \frac{180}{\pi} (\theta_d - \theta) \quad (6)$$" and "$$k_p = a = -b_1 = (K_m G_p \frac{180}{\pi} / R)$$".
- Script quotes (`calc_actuator_model.py` lines 3-8, 13-16, 22-25, 30, 36): "It assumes that the gain used in servo uses units of gain/deg instead of gain/raw_pos. The ST-3215-C047 model data is used."; `tau_stall = 30 * 9.8 / 100`, `i_stall = 2.7`, `Km = tau_stall / i_stall`; `V_rated = 12`, `i_nl = 180e-3`; `R = 1 # Ohm`; `Gp_p_deg = 12`.
- Reproduction (run this session): Km = 2.94/2.7 = 1.0889 N*m/A; kp = Km * Gp * (180/pi) / R. With Gp = 12: 748.66 (matches Gregory's own `so101.xml`: `kp="748.66"`). With Gp = 16: 998.22 (matches the official SO-ARM100 MJCF). So the official MJCF used 16, the repo's current script uses 12; the "assumed 16" is not in the repo at `58ae9dd`.
- Assumptions made and whether sourced: (i) error in degrees, "V = Gp*e" with Gp = P register value directly: unsourced, stated as an assumption; (ii) R = 1 ohm: unsourced and contradicts the same script's stall data (12 V / 2.7 A = 4.44 ohm), which inflates the modelled 12 V stall torque to Km*12/1 = 13.07 N*m versus 2.94 N*m rated, a 4.44x error; (iii) no measurement against hardware.
- Implied `pid_scale`:
  - Torque-level (our law, kp = 998.22 N*m/rad, P = 16): `pid_scale = P * tau_stall * 651.899 / kp`: tau 1.32 -> 16*1.32*651.899/998.22 = **13.8**; tau 1.912 -> **20.0**; tau 2.94 -> **30.7**. (Caller's "~15" is the 5 V case.) Saturation after pid_scale/P = 0.9 / 1.2 / 1.9 counts.
  - Gregory's own units (V = P * e_deg, supply V): duty = P*e_deg/V_supply, per count 0.087891 deg, so `pid_scale = V_supply / 0.087891` = 56.9 (5 V), 84.2 (7.4 V), **136.5** (12 V). Cross-check: kp with R corrected to 4.444 ohm is 998.22/4.444 = 224.6, and 16*2.94*651.899/224.6 = 136.5. Same number, so the two conversions are consistent.
- Verdict: **rejected**. The unit assumption is unsourced and is contradicted by 3 orders of magnitude by the measured evidence in 1.2 (136 vs ~4000 counts per full duty); the caller's reading (implausible as literal register scaling) is confirmed.

### 1.2 Rhoban BAM (and Feetech's own fork)

- URLs: https://github.com/Rhoban/bam (`bam/feetech/actuator.py`, `bam/feetech/record.py`, `bam/params/feetech_sts3215_7_4V/m1.json`, `docs/identification/actuator_modeling.rst`); paper https://arxiv.org/pdf/2410.08650v1 (cited by the repo README, "Extended Friction Models for the Physics Simulation of Servo Actuators", ICRA 2025; the Feetech model is in code and the HF raw-data zip, not fetched: https://huggingface.co/buckets/Gregwar/bam_data/resolve/feetech_sts3215_raw.zip).
- Code quotes (`bam/feetech/actuator.py`, class `STS3215Actuator`, docstring "Feetech STS3215 7.4v"): `vin=7.4, kp=32,` then "# This gain, if multiplied by a position error and firmware KP, gives duty cycle", "# It was determined using an oscilloscope and STS3215 actuators", "# here, firmware_kp = kp", `error_gain=0.166,`, "# Maximum allowable duty cycle, also determined with oscilloscope", `max_pwm=0.97,`. Control law lines 146-155: `duty_cycle = (self.q_target_smooth - q) * self.kp * self.error_gain * self.model.error_gain_ratio.value`, clamp to +/-`max_pwm`, `return self.vin * duty_cycle`. A commented-out alternative `# self.error_gain = 0.001 * np.rad2deg(1.0)` is present.
- Units of the error are radians: `record.py` stores `position = np.deg2rad(io.get_present_position([1])[0])` and writes the firmware P directly with `io.set_P_coefficient({1: args.kp})` (sweep `kps = [4, 8, 16, 32]` in `all_record.py`). The base class docstring says error_gain "Converts ``kp * Δq`` to a duty cycle in [−1, 1]".
- Identified parameters (m1.json, supply `vin` 7.4 V in model; the recorded per-log supply is the `input_volts` field read from the servo, raw logs not fetched): `"kt": 1.1776311631627974, "error_gain_ratio": 1.0049367060648848, "R": 2.478681934101461, "armature": 0.02608291141307205, "friction_base": 0.05152047758105413, "friction_viscous": 0.05989161871380604, "max_velocity": 5.2883481319359`.
- Implied `pid_scale` (duty = P * g * e_rad = P * e_counts / pid_scale, so `pid_scale = 1 / (g * 2*pi/4096)`):
  - g = 0.166: 1/(0.166 * 1.53398e-3) = **3927**.
  - with the identified ratio 1.00494: 1/(0.166 * 1.00494 * 1.53398e-3) = **3908**.
  - Saturation at P = 16 with max_pwm 0.97: 0.97 / (16 * 0.166 * 1.53398e-3) = 238 counts (20.9 deg).
- Feetech's own fork https://github.com/ftservo/ftservo-bam (Apache-2.0, "Copyright 2026 ftservo", same STS3215 class, `error_gain=0.163`, `max_pwm=0.97`, same m1.json): 1/(0.163 * 1.53398e-3) = **3999.4** (3979.7 with ratio 1.00494). This is not an independent measurement of the same bench (it is a Feetech-modified fork of BAM), but a vendor-side adjustment to 0.163 lands on 4000 to four digits.
- Caveat on torque-per-duty: BAM's identified kt/R gives a duty-100 % stall of kt*Vin/R = 1.1776*7.4/2.4787 = 3.52 N*m, 1.84x the datasheet 1.912 N*m at 7.4 V (kt, R and the friction terms are fit jointly, so this can be a fit degeneracy rather than physics). In torque space BAM's static stiffness at P = 16 is 16*0.166*1.00494*3.516 = 9.38 N*m/rad; our law with datasheet tau_stall would need `pid_scale = 16*1.912*651.899/9.38` = **2123** to match it. This sets the lower edge of the plausible range.
- Doc inconsistency (confirmed): `docs/identification/actuator_modeling.rst` says "u = error_gain * kp * (target - position) is the voltage command", while the code treats it as duty and multiplies by `vin`. The code, the oscilloscope comment and the class docstring agree on duty, so duty is used here.
- Verdict: **load-bearing (measured)**: 3927 / 3908.

### 1.3 Third-party memory-table transcription (aifitlab)

- URL: https://aifitlab-wiki.super.site/feetech-servo-motor-docs/feetech-sts-servo-memory-table-analysis (HTML fetched; strings confirmed in the page source).
- Verbatim cell text: address 21 "Proportional gain (scaled by 1/4)", range "0 ~ 254"; address 22 "Derivative gain (scaled by 1/8)", "0 ~ 254"; address 23 "Integral gain".
- Implied `pid_scale`: "scaled by 1/4" alone says the effective gain is P/4 in the firmware's output unit; the output unit is not named in this table. If that unit is the 0.1 % duty unit (see 1.4), duty = (P/4)*e_counts/1000, so `pid_scale` = 4*1000 = **4000**.

### 1.4 Feetech's own documentation (official wiki)

- URL: https://ftservo.github.io/ftservo-wiki/ (site of https://github.com/ftservo/ftservo-wiki; its `sdk/README.md` calls the linked SDKs "Official SDK submodules"; the GitHub account's ownership by Feetech is established only by this self-description plus the feetechrc.com links in its product manifests). Files read: `docs/reference/parameter/memory-sts.md` (Chinese) and `docs/en/reference/parameter/memory-sts.md` (English), commit `f1387d3`, 2026-10-05.
- Quotes (English file): address 21 (0x15) "Position loop P (proportional) coefficient | 1 | – | R/W | 0~254 | None | Proportional coefficient controlling the motor (1/4)"; address 22 "Position loop D (derivative) coefficient ... Derivative coefficient controlling the motor (1/8)"; address 23 "Position loop I (integral) coefficient ... | 0 |". Chinese original of row 21: "控制电机的比例系数(1/4)". Address 16 "最大扭矩 ... 1000 ... 0~1000 | 0.1%" (Max torque default 1000, unit 0.1 %). Address 60 (0x3C) Present load: "0.1% | Duty cycle of the output driving the motor; BIT10 is the direction bit" (Chinese: "当前控制输出驱动电机的电压占空比"). Address 25: "最大积分值=积分限制值*4" (max integral = limit * 4). Address 24 "最小启动扭矩 ... 0.1%".
- Reading: the firmware's output stage is expressed in 0.1 % duty units (0..1000), P is applied as P/4 and D as D/8 (Kd carries a different factor). No register-level formula for the error unit or loop period is published.
- Implied `pid_scale`: output(0.1 % units) = (P/4)*e_counts, duty = output/1000, so `pid_scale = 4*1000` = **4000**; D term `D/8/1000` = `(D/2)/4000`, so with a single `pid_scale = 4000` the sim's `d` should be D/2 (D=32 -> 16). The per-cycle time base of `e - e_prev` is unpublished, so the D conversion is an inference. The I term has no published scaling (LeRobot writes I = 0, so it is moot for the SO-101).
- Cross-check with 1.2: the official table gives exactly 4000, the oscilloscope gave 3927 (-1.8 %), the Feetech fork gives 3999. Three independent-looking routes agree within 2 %. (Not fully independent: the 1/4 and 1000 combination is an interpretation; the oscilloscope number does not depend on it.)
- Verdict: **load-bearing (documentary)**.

### 1.5 Published STS3215 static stiffness / position error under load

- Robonine bench test: https://robonine.com/testing-of-feetech-sts3215-servomotor-backlash-repeatability-and-torque/ . Quotes: "In the dynamic test with a 10 kg·cm load, the measured mean absolute position deviation was 22.5 encoder steps, corresponding to approximately 2 degrees"; "With a 15 kg·cm load in the dynamic test, measured mean absolute position deviation is 30 encoder steps or about 2.6 degrees."; comment reply "all the torque figures in the table were taken at 12 V."; table row "Firmware Dead Zone | Command input < 10 encoder steps | No motion observed | Built-in 10-count deadband". P/I/D settings are not stated (factory default P is 32 per the memory table).
- Conversion: K = tau/theta. 15 kg.cm = 1.47 N*m at 30 steps (0.04602 rad): K = 31.9 N*m/rad. 10 kg.cm = 0.98 N*m at 22.5 steps (0.03452 rad): K = 28.4 N*m/rad. `pid_scale = P * 2.94 * 651.899 / K`: for P = 32, 1920 (15 kg.cm) and 2160 (10 kg.cm); for P = 16, 960 and 1080. For the 4000 candidate at P = 32 the law predicts a static offset of 62.5 counts (15 kg.cm) and 41.7 counts (10 kg.cm), versus 30 and 22.5 measured (ratio 2.1 and 1.9).
- Weighting: **weak, not used for the point value.** The offsets are mean absolute deviation during motion (dynamic test), P unknown, a 10-count firmware deadband is reported (that would bias the offset low), and the 12 V torque per duty at 12 V is assumed to be the 2.94 N*m rating while the same article measures a static stall above 30 kg.cm. It does bound the plausible range from below (~2000 if P = 32; ~1000 if P = 16) and is consistent with BAM's torque-level 2123.
- No published step response or holding-torque-versus-error curve for the STS3215 was found (searches: Feetech docs, Waveshare wiki, forum/GitHub searches).
- LeRobot issue 3400 (see 2): P = 16 settles 63 ticks from target, P = 32 settles 26.7 ticks (shoulder_pan, unit "ticks" not defined in the thread; assumed encoder counts). Error scales ~1/P (63*16 = 1008 vs 26.7*32 = 854), as a stiction offset should: error = ps * duty_f / P. With friction duty duty_f = tau_f / tau_stall: `pid_scale = P * e * tau_stall / tau_f` = 16*63*1.32/tau_f = 1331/tau_f: tau_f 0.05 N*m (BAM friction_base 0.0515) -> 26600, 0.1 -> 13300, 0.2 -> 6650, 0.3 -> 4435. Friction of the loaded shoulder_pan bearing stack is unknown, so this gives only a weak lower bound ("friction >= 0.3 N*m or pid_scale >= 4400"); it does not contradict 4000 but cannot confirm it.

| Evidence | Implied `pid_scale` | Weight |

**Recommendation: `pid_scale = 4000`** for the P term (range 2100-4000, measured band 3900-4000). Reasoning: two routes that do not depend on any torque assumption (oscilloscope duty, official register units) agree within 2 %. 8192 is unsupported and doubles the sag. The only evidence pointing lower (BAM torque level, Robonine) is entangled with a different torque-per-duty than the datasheet-derived motor model, so it is better handled by checking the motor model than by lowering `pid_scale`. This is "best supported", not "pinned": no source states the error unit and loop period in one place, and a hardware holding-torque-versus-error measurement would pin it (suggested check: 100 g at 20 cm on a stiff joint, read present position at P = 16 and 32).

### 1.7 Effect on the caller's numbers

Sag = duty_needed * pid_scale / P. From the caller's duties (shoulder_lift 0.199 at 102 counts, elbow 6.0 deg = 68.3 counts so duty 0.133, both at pid_scale 8192, P = 16): at 4000 shoulder_lift 49.8 counts = 4.38 deg, elbow 33.3 counts = 2.93 deg; at 3927 48.9 counts (4.30 deg) and 32.7 counts (2.88 deg); at 2000 24.9 counts (2.19 deg) and 16.7 counts (1.46 deg). Full duty at P = 16 is reached at 1.0*4000/16 = 250 counts (22 deg); at the factory P = 32, 125 counts (11 deg).

## 2. Reports on how SO-101/SO-100 hold pose with LeRobot defaults (P=16, I=0, D=32)

Defaults confirmed in code at `200ee53` (`src/lerobot/robots/so_follower/config_so_follower.py` lines 45-47: `position_p_coefficient: int = 16`, `position_i_coefficient: int = 0`, `position_d_coefficient: int = 32`; written in `so_follower.py` lines 188-190).

- "Too soft / dead-band" (closest to droop), https://github.com/huggingface/lerobot/issues/3400 (opened 2026-04-17, "P=16 not driving shoulder_pan to target position reliably"): "With P=16, the PID output torque is insufficient to overcome static friction when position error is small, creating a dead-band. As a result, commanding the same goal position from different approach directions lands the arm at different physical positions." Follow-up comment (user 0o8o0-blip): "Okay so i did a collection with p=16 and p=32. The were 63 and 26.7 ticks from target respectively." The thread is about unloaded settling accuracy, not gravity sag.
- Fix path: https://github.com/huggingface/lerobot/pull/3555 (2026-05-10, "Make SO follower position P gain configurable"): "This change preserves the established default of `16` to avoid changing stiffness across all motors without broader hardware validation, while allowing affected users to opt into `position_p_coefficient=32`". Also the LeKiwi code comment `src/lerobot/robots/lekiwi/lekiwi.py:196`: "# Set P_Coefficient to lower value to avoid shakiness (Default is 32)".
- "Too stiff / unstable": https://github.com/huggingface/lerobot/issues/1333 (2025-06-17, SO-100 wrist_roll): "Default P_Coefficient (16) appears too high for wrist_roll motor"; reducing wrist_roll P from 16 to 4 improved the reported standard deviation from 95.596 to 59.976. This is a wrist-roll teleoperation instability report with no stated cause.
- Gravity droop/sag with torque on, at default gains: **none found.** GitHub issue searches (unauthenticated API, rate-limited after the first dozen queries) and web searches returned no report of steady-state arm sag, and **no explicit "holds pose well" report** was found either. The one "sag" hit, https://www.ay-robots.com/fix/arm-twitches-then-sags (a vendor page, last updated 2026-08-09), concerns brownout cut-out under load ("a supply that cannot hold voltage through that spike sags far enough for the servos to latch an undervoltage condition and cut torque"), which is not a position-loop effect (the page also says 7.4 V where the stock kit uses 5 V, so treat it with care). LeRobot's SO-101 doc says only: "The follower arm uses 6x STS3215 motors with 1/345 gearing. The leader, however, uses three differently geared motors to make sure it can both sustain its own weight and it can be moved without requiring much force." (https://huggingface.co/docs/lerobot/so101, `docs/source/so101.mdx:35`).
- Not searched (not retrievable by these tools): HF forum search pages, Discord, Reddit.

### 5.2 Friction coefficients

No peer-reviewed or vendor measurement of PLA-on-PLA static or kinetic friction, nor PLA-on-TPU, was found in this run (searches returned PLA-on-steel/metal and composite studies; a Bulgarian static/kinetic study, https://tribology.rs/journals/2024/2024-1/9-1546.pdf, tests PLA against steel and its values are in figures only). What was found:

- PLA against CoCr pin, FDM, pin-on-plate, ASTM G133, 50-100 N, 0.5-1 mm/s (https://revmaterialeplastice.ro/pdf/19%20CHISIU%201%2021.pdf, Mater. Plast. 58(1) 2021): "The COF values of 3D printed ABS sample for the longitudinal direction are 0.297 and 0.375 at 0.5mm/s and 1mm/s, respectively, under 50 N load. ... Regarding the 3D printed PLA samples, it can be said that the change in the COF values is almost the same with those obtained from 3D printed ABS samples." Orientation: "Transverse direction (T.D) of the 3D-printed samples shows higher coefficient of friction (COF) values than the longitudinal direction under all applied loads and sliding speeds." The paper also cites: "Pawlak W. [12] obtained a COF value of about 0.48 in coupling PLA/metal pair." Kinetic only; no static value.
- PLA and TPU against C45 steel disc, tribometer, 50/150 N (https://revmaterialeplastice.ro/pdf/6%20BRAILEANU%20%203%2023.pdf, Mater. Plast., year not printed in the extracted text, file name suggests 2023): "a friction coefficient of 0.146 was determined for PLA 1 and 0.16 for PLA 2 at 0.1 mm/s under a force of 50N"; "Regarding TPU 93A, friction coefficients were notably higher. At 50N and 0.1 mm/s, the coefficients were 0.199 for TPU 93A 1 and 0.21 for TPU 93A 2"; orientation: "the anisotropy of the materials, represented by the two orientations (1 and 2), played a substantial role in the friction coefficients". Kinetic only.
- Not verified: engineering tables quoting static ~0.35-0.40 and kinetic ~0.30-0.35 for PLA (appeared in a search-result summary only; unverified).

Chosen for the sim (assumptions, labelled): PLA jaw on PLA cube **0.40** sliding (static-like value from the 0.30-0.375 kinetic PLA-on-metal range plus the 0.48 cited value; a kinetic-only reference would be 0.30; real PLA-on-PLA depends on print orientation, layer lines and surface finish, the cited studies show +/-10-15 % between orientations). PLA on TPU 95A tip **0.55** = 0.40 * (0.199/0.146 = 1.36) from the TPU 93A/PLA ratio on steel; TPU is not part of the stock jaws (5.3), so this is only for the optional compliant gripper. Re-measure with an inclined-plane test (3 cubes, 3 orientations) if grasp stability turns out to be sensitive: a 0.30-0.55 sweep is the sensible range.
